### 1.1 真正的实时开关

本机 `/usr/lib/libutils.so` 导出的 `APP_TRACE`（地址 `0xdb90`）反汇编显示：

1. 先调用 `real_time_log_store`。
2. 读取 `debuglog_enable` 并转换为整数；为 0 则直接返回。
3. `log_save_en` 为字符串 `1` 时调用 `history_log_save`。
4. 再读取 `syslogd_enable` 并按 0～4 选择输出分支；3 分支直接打开并写入 `/tmp/.systemlog`，不经 syslogd。
5. 页面日志分支具有文件大小检查，超过约 320000 字节时 unlink 后重建；也处理 `clear_syslog`。这是静态实现证据，本轮没有主动触发轮转。

`ltemanage` 和拨号程序的字符串/符号中均存在 APP_TRACE，且运行进程加载该库。以上结论针对已定位的 APP_TRACE 路径，不声称覆盖所有固件、所有日志函数。

**含义：**仅启动标准 syslogd 或读取不存在的文件，不能保证获得同样的模组 AT 日志；对于该路径，页面实时日志要求总开关非零且输出模式为 3。调用现场会读取 NVRAM，提示可能无需重启业务进程，但即时生效与所有调用方是否另有缓存仍需受控实验。

另一路 `real_time_log_store`（`0xd244`）在总开关判断前执行，但同时要求 `log_onoff=1`、`enable_remote_manager=1`、`retmgr_con_status=3`，写 `/tmp/root/real_time_log.txt`。本机这些条件不满足。**不采用伪造厂商远程管理连接状态作为绕过方案，也不修改固件库、注入进程或抢占模组串口。**

### 1.2 历史保存的实际链路

- `history_log_save`（`0xd06c`）以追加方式写 `/tmp/root/FF_BKDATA_YYYY-MM-DD.txt`，与最终持久目录分开。
- `/sbin/sd_log_mgmt` 是指向 `/sbin/rc` 的链接；本轮采样时未运行。
- rc 二进制字符串包含 `log_save_itv`、`log_save_en`、`save_log_now` 及 `gzip -c /tmp/root/%s >> /jffs/%s.gz`。这支持“RAM 中先积累、周期压缩保存”的实现判断，但没有开启开关验证调用时序、服务启动方式或更新间隔的生效方式。
- 追加 gzip 的实现线索要求后续验证**多 gzip member 串接**，解析不能只读取第一段压缩数据。
- 当前页面输入校验写 1～999999，配置描述却写 0～65535，实读值为 300。这是厂商固件自身范围不一致；建议首版采用 **1～65535 秒，默认 300**，以受控实测确认，不盲从任一页面上限。
- 对 APP_TRACE 路径，`log_save_en=1` 仍依赖 `debuglog_enable` 非零；历史保存不要求 `syslogd_enable=3`。不能只回读一个历史开关就宣称正常记录。

## 2. 建议的用户体验

在现有 WPF 设备工作区增加“日志”，内部提供“实时日志 / 历史日志 / 分析”。沿用当前共享控件、中文与浅色/深色/系统主题，不整体改版，不恢复 React 或内置 SSH。

### 2.1 实时日志

- 进入页面先探测配置与可用日志源；用户点击“开始采集”后才建立采集会话。
- 原总开关及页面输出已满足时，直接读取，不改配置。
- 未满足时，提供“临时启用并采集”：展示将调整的值，保存原值及原本是否存在，只调整必要的 `debuglog_enable=1` / `syslogd_enable=3`，**不自动 nvram commit，不重启拨号或整机**。
- 必须明确：该方式实现的是“用户不必预先开启”，不是“两个 NVRAM 值始终保持关闭还能生成同样日志”。如果要求后者，需要另一项方案，目前没有证实独立且无副作用的入口。
- 临时改变输出模式可能暂停原有远程/USB输出；若历史开关原为 1 而总开关为 0，启用总开关还可能开始历史写入。确认窗口说明实际联动，不静默处理。
- 停止采集、会话租期结束、设备/Server 切换及受控退出时释放采集资源；恢复只针对本功能实际改过且当前值仍匹配本功能写入值的参数。发现用户或其他管理端改动则不覆盖，显示冲突。
- 多个客户端共用设备的一份采集源；最后一个使用者释放后才恢复，不能互相关掉日志。历史保存正式开启后，总开关不能被实时会话清理错误关闭。
- 提供暂停滚动、继续跟随、关键词检索、复制、清空本地显示、导出已采集文本；“清空显示”不删除设备日志。暂停显示不等于停止采集。
- 有界缓存、增量读取、文件删除/重建/截断检测、跨块多行与编码处理；断线、轮转或积压导致缺段时明确提示，不能显示成无损连续日志。
- 非正常强杀无法保证立即恢复临时参数；Probe 再启动时按保存的临时状态及当前值核对。不得承诺断电/外部 commit 后绝对回滚，更不引入隐藏常驻守护进程来伪造保证。

### 2.2 历史目录和文件发现

默认依次探测：

1. `/tmp/third_party/data`
2. `/jfss`（用户给定路径，保留兼容）
3. `/jffs`（本次实机确认）

解析路径别名，按实际目录/文件身份去重；采用有界目录扫描，不全盘递归。上述位置没有文件时显示已检查路径并允许输入绝对目录；权限不足、无法读取、目录不存在与确实为空分别表达。

主匹配规则为 `FF_BKDATA_YYYY-MM-DD.txt.gz`。同时把 `/tmp/root/FF_BKDATA_YYYY-MM-DD.txt` 作为“尚未持久化的缓存日志”单独标记，不能伪装成已经落盘的历史文件。

| 开关与文件状态 | 行为 |
| --- | --- |
| 已发现历史文件，不论当前开关 | 允许查看、导出及可用的分析；历史开关关闭不阻止读取旧记录 |
| 未发现文件且历史开关关闭 | 提示“历史保存未开启，已检查目录未发现历史日志”，提供自定义路径和独立开启按钮 |
| 已开启但尚无文件 | 提示可能尚未到保存周期，并检查 RAM 缓存、服务/目录状态；不是笼统报“未开启” |
| 无法读取配置或目录 | 显示检查失败及原因，不把未知状态当作关闭/空目录 |

“开启历史保存”单独确认：间隔默认 300 秒，首版建议 1～65535；明确展示总开关的必要联动、写入位置与闪存写入影响。设置和持久化分开：先回读确认运行值，并验证缓存/保存机制；“保存到设备配置（commit）”为独立显式操作。服务启动/重载须在受控实验确认后使用最小动作，不直接套用整机重启或通用 service restart。

### 2.3 导出

- 单个或批量导出原始 `.txt.gz`；可选解压为 `.txt`，尽量保持原始字节和名称，不改写日志时间或 AT 内容。
- 原始文件走现有 File / Repository 的传输与完整性校验，不从 SSH 或持续 Exec 获取产品日志内容，也不复制文件状态机。
- 对仍被追加的当日 gzip / RAM 文件，先生成有空间和大小约束的快照再传输；不停止原日志进程。快照生成前后核对变化，明确截止时间/不稳定状态，不能把正在追加的压缩尾部当作完整归档。
- 完整性校验通过不等于原文件时间范围完整；截断 gzip、损坏成员、导出时仍在变化等分别提示。临时快照仅清理本次拥有的文件，不删除历史文件。
- Server 已取得的原始资产在设备离线后仍可下载；同时保持现有资产身份与 committed/released/Task RESULT 分离语义。

### 2.4 分析及厂商解析器

本轮实现阶段只做原文预览/检索、文件输入接入和“解析器尚未配置”的真实状态；**厂商 AT 语义解析等待用户提供样本和确认字段后实现**。不建立空类/空目录冒充完成解析器。

先在设计中保留边界：输入为原始文件/多成员 gzip 和设备/模组上下文，输出为标准事件、来源文件与行/字节位置、解析器名称/版本及未识别记录。解析放在 Go 管理端业务层，Probe 不含厂商 AT 语义或 AI 排障；当前不接入 LLM、MCP 或 Phase 8。

后续样本评审的建议目标（不是已定格式）：

- 根据正文有效时间戳计算日志覆盖范围，处理多行响应、跨天、多文件重叠、设备时间跳变和无时区时间；文件名仅作提示。
- 汇总有记录的基站，候选字段包括 PLMN、制式、TAC/LAC、Cell ID、频段/频点、PCI、信号指标，以及首次/最后出现、记录次数。
- 区分驻留小区和邻区；不同制式采用适当身份字段，不只按 PCI 去重。不补造缺失信息，不把观察时间段推断为连续驻留时长。
- 混合厂商、双模组/多 SIM、未知 AT、解析失败均保留原文和定位；无法识别时允许原文导出，不宣称语义分析成功。
- 基站之外的拨号、注册、切换、断网等分析项，等样本和用户确认后再定。

## 3. 技术改造与需要批准的契约

当前没有原生日志订阅功能。`internal/task/service.go` 保留任务记录，`RemoteDirectory` 目前通过有限 Exec 读取目录；因此不能每秒创建一个新任务模拟长期实时日志。现有 `/api/v1/events` 明确只有资源失效通知，不能把它默认为日志正文流。

推荐最小闭环：

| 层 | 改造职责 |
| --- | --- |
| Probe C++11 | 日志能力检测、固件适配、临时设置生命周期、独立有界文件采集、目录发现与导出快照；不解析 AT |
| Gateway / Protocol | 增加协商能力 `device_logs_v1`（暂定）、结构化采集控制和有界日志批次；严格绑定设备 Session/采集代次，旧 Probe 显示不支持 |
| Go Log Service / Management | 会话/订阅协调、设置联动、游标缓存、历史发现/导出编排；通过既有配置/文件服务协作 |
| HTTP API | 专用状态、采集会话、游标读取、历史清单、配置及导出入口；所有写操作沿用幂等键和结果不确定处理 |
| WPF Client / Desktop | 仅调用公开 API；日志三个视图、异步操作、取消与设备/Server隔离；不在页面里拼接固件业务命令 |
| 生成器 | 首版不扩展模板工程格式；确认存在型号差异后再针对日志路径/适配描述做必要最小扩展，不预建大框架 |

传输建议：复用现有协议帧和连接，为采集增加有界结构化批次，不建立新 Tunnel/任意端口，不把 SSH 字节流或无限 tail 塞进控制链路。日志低优先级，限制单批序列化后大小和发送速率（建议起点约 16 KiB/秒/设备，最终依据真机负载），不得阻塞心跳、任务及文件 ACK。携带采集代次、顺序、字节游标和缺口状态，超出预算可明确丢弃/提示而非无限排队。

Server 对客户端提供 HTTP 增量游标读取；保留现有 WebSocket 的“资源变化提示”语义，不改成日志正文流。界面实时目标为典型负载下约 1～2 秒延迟，不承诺断网、轮转与过载下绝对无损；原始历史导出承担完整文件获取。

**以上包含新的协议/API语义，必须在用户审核后形成正式 ADR，再同步 PROTOCOL/API/ARCHITECTURE。当前计划不是 Accepted 设计，不以功能授权跳过协议确认。** 若实测日志量无法在预算内满足需求，先返回评估，不自动实施暂缓的数据面扩展。

## 4. 实施顺序与验收

### A. 受控固件验证（批准后首先执行）

- 保存原始开关及其存在性，短时验证总开关 0/1 与输出模式组合，观察真实日志产生，而非只检查 nvram 命令成功。
- 验证即时生效、退出恢复、原输出目的地影响；不 commit、不重启拨号进程、不触碰模组串口。
- 单独验证历史关闭/开启、间隔调整、总开关联动、sd_log_mgmt 启动/生效方式、gzip 追加和缓存清理，恢复原设置；此试验会生成少量日志文件，须纳入用户批准范围。
- 若必须重启关键服务/整机或写入永久配置才能继续，则停止该依赖项并另行说明，不能将计划批准理解为任意设备改动授权。

### B. 实时日志闭环

协议/能力 → Probe采集与恢复 → Log Service/API → WPF。验证关闭状态下开始、已开启时不干预、多个观察者、暂停显示、主动停止、断线、切换、退出、轮转/截断及恢复冲突；显示连续性/缺段状态。

### C. 历史发现、设置和导出

覆盖路径差异/软链接去重/自定义路径、开关与文件组合、区间输入、设置回读、历史依赖、稳定快照、多文件/损坏 gzip、多成员 gzip、空间不足与导出中断。

### D. 原文查看与后续解析边界

完成原文查看、输入接入和未支持状态；用户提供样本后再评审规范化事件、基站汇总与其他分析项，并建立厂商样本回归。首版不得把这一项写成“各厂商解析完成”。

### 验证环境

按 DEVELOPMENT 执行受影响的 Probe CTest、Go 单元/集成/race、WPF交互和布局检查。重点验证高日志量不影响心跳/任务/文件；原始文件导出逐字节/既有摘要一致；全部异常状态不伪报成功。

本次实际设备为 **MIPS little-endian**，ADR-058 最近验证的 Probe 产物为 ARMv7，不能直接部署到此设备。实施前在既定构建机核对可用 mipsel/uClibc 工具链，并对必要构建扩展提出明确方案；不擅自更换默认编译机、默认工具链或部署 ARM 文件。
